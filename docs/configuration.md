# Configuration

`ccc-agent` reads a JSON runtime config. JSON is used deliberately so the trusted
runtime remains stdlib-only Python.

## Search order

The CLI loads config from the first available source:

1. `--config PATH`
2. `$CCC_AGENT_CONFIG`
3. `/etc/ccc-agent/config.json`
4. `/opt/ccc-agent/config/config.json`

`ccc-agent setup --system` writes `/etc/ccc-agent/config.json` by default.
`ccc-agent setup --user` writes `~/.config/ccc-agent/config.json` by default.

See [`config/config.example.json`](../config/config.example.json) for a complete
annotated example.

## Minimal shape

```json
{
  "state_dir": "/storage/user/.ccc-agent",
  "backend": "branchfs",
  "branchfs_bin": "/usr/local/bin/branchfs",
  "user": "<user>",
  "home_subdir": "<home-subdir>",
  "confinement": "bwrap",
  "bwrap_bin": "/usr/bin/bwrap",
  "roots": [
    {
      "name": "storage",
      "base": "/storage",
      "store": "/opt/branchfs_branches/storage",
      "visible": "/storage",
      "home_subdir": "user/<home-subdir>",
      "hide_paths": ["user/<home-subdir>/.ssh"]
    }
  ],
  "policy": {"mode": "workspace-auto"}
}
```

## Top-level keys

| Key | Purpose |
|---|---|
| `state_dir` | Session metadata, review artifacts, mountpoint directories, and control socket paths. The agent must not be able to modify it directly. |
| `backend` | Usually `branchfs`. Test/demo code may use fake backends. |
| `branchfs_bin` | Path to the BranchFS CLI. |
| `branchfs_timeout_seconds` | Timeout for BranchFS CLI calls; default is 30 when generated by setup. |
| `user` | User name used for `/home/<user>` and sandbox env. |
| `home_subdir` | Policy alias for mapping `/home/<user>` to the corresponding subpath of a protected root. |
| `confinement` | `bwrap` for real containment, `none` only for debugging the policy pipeline. |
| `bwrap_bin` | Path to bubblewrap. |
| `bwrap_proc_mode` | `bind`, `ro`, or `fresh`; default generated config uses `bind`. |
| `container_run_access` | Whether to bind ambient `/run`, read-only `/var`, and device-capable `/dev` into the sandbox. |
| `bwrap_ro_binds` | Optional read-only binds for agent runtime files that live outside the sandbox view. Prefer destinations outside protected roots. |
| `bwrap_setenv` | Extra environment variables passed into the clear-env sandbox. |
| `roots` | Protected BranchFS roots. |
| `policy` | Default policy applied to runs unless overridden by CLI flags. |
| `workspace_admission_roots` | Maximum operator-selected domain for trusted dynamic workspace roots. Paths are CCC-canonicalized and must be under protected storage. Defaults to the protected visible roots for compatibility. |
| `allow_protected_root_workspace` | Permit a dynamic workspace to equal its admission/protected root. Default `false`; ordinary dynamic roots must be strict descendants. |
| `session_delta_routing` | Enable optional per-logical-session delta routing. Default `false`. The outer BranchFS+bwrap boundary is unchanged. |
| `session_delta_routing_vendors` | Explicit routing vendor allowlist. Defaults to `["codex"]`; it has no effect while routing is disabled. |

## Protected roots

Each root describes one BranchFS base/store/view relationship:

| Key | Purpose |
|---|---|
| `name` | Stable root label used in session metadata. |
| `base` | Real underlay path read through by BranchFS. |
| `store` | BranchFS metadata/delta/tombstone store. Must be hidden from the agent. |
| `visible` | Path where the branch view appears inside the sandbox. |
| `home_subdir` | Optional subdirectory of this root that should be bind-mounted to `/home/<user>`. |
| `hide_paths` | Literal relative prefixes hidden preventively by BranchFS. |

If two visible paths alias the same real data, protect them with one root and
bind aliases from the same branch. Do not create independent BranchFS roots for
the same underlying bytes.

## Dynamic workspace admission

Authenticated MCP, Codex, or Hermes workspace metadata is additionally bounded
by an operator ceiling:

```json
{
  "workspace_admission_roots": [
    "/storage/user/Projects",
    "/storage/group/approved-projects"
  ],
  "allow_protected_root_workspace": false,
  "session_delta_routing": false,
  "session_delta_routing_vendors": ["codex"]
}
```

Every authoritative dynamic root must be an existing non-symlinked directory,
must remain under a protected BranchFS root after `/home/$USER` alias
canonicalization, and must be a strict descendant of an admission root. Selecting
an admission root or protected root itself requires the explicit broad-root
switch. Empty trusted replacement sets remain valid and revoke only the relevant
logical session's dynamic roots.

An explicit `ccc-agent run --workspace` remains an operator launch decision, but
it is normalized, checked beneath protected storage, and identity-revalidated
before the branch session is created. Dynamic admission ceilings do not weaken or
replace the outer BranchFS+bwrap containment boundary.

## Agent runtime state

By default, known Codex/Claude/Hermes runtime paths are direct read-write binds
over the BranchFS home view:

```json
{
  "protect_agent_state": false,
  "ensure_agent_state_dirs": true,
  "agent_state_binds": [
    "/home/<user>/.codex",
    "/home/<user>/.claude",
    "/home/<user>/.hermes",
    "/home/<user>/.claude.json",
    "/home/<user>/.local/bin/claude",
    "/home/<user>/.local/share/claude",
    "/home/<user>/.local/state/claude",
    "/home/<user>/.cache/claude-cli-nodejs"
  ]
}
```

These paths are agent/system state, not project deliverables. They persist
immediately and are not committed, reviewed, or rolled back by BranchFS. Set
`protect_agent_state: true` or pass `ccc-agent run --protect-agent-state` only if
you intentionally want those paths reviewed as branch deltas.

## Credential options

| Key | Purpose |
|---|---|
| `cred_mounts` | Narrow read-only bind overlays for special cases. Do not use for whole `~/.codex`, `~/.claude`, or `~/.hermes` trees. |
| `cred_mask` | Paths overmounted with `/dev/null` when present. |
| `cred_env` | Supervisor reads a host env/file/json value and passes it into the sandbox as an environment variable. |

OAuth-style agent logins commonly require writable token/state files, so they are
usually handled through shared `agent_state_binds` rather than read-only
credential mounts.

## Agent plugins

`agent_plugins` maps agent names to read-only assets that `ccc-agent run` may
mount for contained sessions. Setup-generated defaults use one native plugin path
per tool:

- Codex: setup enables/trusts the bundled plugin in Codex config; runtime mounts
  the package-owned plugin cache path read-only.
- Claude: setup materializes a complete seed from pip package data; runtime
  mounts it read-only and sets `CLAUDE_CODE_PLUGIN_SEED_DIR` inside bwrap.
  Setup-managed settings contain only
  `enabledPlugins["ccc@ccc-agent"] = true`; hooks stay inside the plugin.

```json
{
  "agent_hook_mode": "plugins",
  "agent_plugins": {
    "codex": {
      "src": "/usr/lib/python3/dist-packages/ccc_agent/assets/plugins/codex-ccc-containment",
      "sandbox_path": "/home/<user>/.codex/plugins/cache/ccc-agent/ccc/0.2.0",
      "ensure_dirs": ["/home/<user>/.codex/plugins/cache/ccc-agent/ccc"],
      "plugin_id": "ccc@ccc-agent"
    },
    "claude": {
      "src": "/opt/claude-seed",
      "sandbox_path": "/opt/claude-seed",
      "setenv": {"CLAUDE_CODE_PLUGIN_SEED_DIR": "/opt/claude-seed"},
      "plugin_id": "ccc@ccc-agent"
    }
  }
}
```

`ccc-agent setup --system` creates `/opt/claude-seed`; user setup creates
`~/.local/share/ccc-agent/claude-seed`. No Claude CLI invocation or image rebuild
is required. To materialize the system seed in a dedicated image layer:

```dockerfile
RUN python -m ccc_agent.claude_plugin --seed-dir /opt/claude-seed
ENV CLAUDE_CODE_PLUGIN_SEED_DIR=/opt/claude-seed
```

The marketplace source must remain at `marketplaces/ccc-agent`: Claude resolves
seed marketplace content from that location rather than trusting build-time
absolute paths in `known_marketplaces.json`.

During runtime setup, ccc-agent also mirrors the seed's CCC marketplace/install
records into the user's `~/.claude/plugins` metadata while preserving unrelated
plugins. Claude 2.1.x otherwise reconciles a pristine home too late for hooks to
be active on the first invocation. Executable plugin files remain in the
read-only seed.

For matching contained commands, the launcher:

1. validates the configured asset/seed directory on the trusted host;
2. bind-mounts `src` read-only at `sandbox_path` when present;
3. creates `ensure_dirs` mount parents inside the sandbox;
4. sets plugin env such as `CLAUDE_CODE_PLUGIN_SEED_DIR` when configured;
5. degrades to process-exit review if the asset is missing.

Generated defaults do not append Codex YOLO args and do not append Claude
`--plugin-dir`. Claude hook definitions stay inside the packaged Claude plugin;
there are no separate Claude settings-level hooks. Manual operator config may
still include `argv` or extra `setenv`, but that is an explicit override.

`ccc-agent setup --system` writes persistent Codex config under `/etc/codex`,
Claude plugin enablement under `/etc/claude-code/managed-settings.d`, and the
system seed under `/opt`. User mode writes equivalent config under the user's
home and materializes a user-local seed.

Set `agent_hook_mode: "disabled"` and `agent_plugins: {}` to disable native
plugin/config setup.

## Policy keys

```json
{
  "hide_patterns": [".env", "*.pem"],
  "policy": {
    "mode": "workspace-auto",
    "allowed_scopes": ["/home/<user>/Projects/my-project"],
    "deny_patterns": [".ssh", ".git/hooks"],
    "ignore_patterns": ["/home/<user>/.cache*"],
    "max_policy_repair_attempts": 2
  }
}
```

- `allowed_scopes` defaults to the run workspace.
- `hide_patterns` and `deny_patterns` are detective glob-style policy rules that
  force review when matching changed paths.
- `roots[].hide_paths` are preventive literal BranchFS hide prefixes.
- `ignore_patterns` remove cache/runtime noise from review and commit.

See [Path policy and secret handling](policy.md) for semantics.

## Security requirements for config

- Config files, plugin assets, and hook scripts must not be writable by the
  untrusted agent.
- `state_dir` and BranchFS stores must not be reachable through agent-visible
  writable paths.
- If a state directory must live under a protected underlay, hide it with
  `roots[].hide_paths` and keep policy deny patterns for `.ccc-agent`.
- Keep runtime/plugin bind destinations outside protected roots where possible to
  avoid creating mountpoint deltas inside the BranchFS view.
